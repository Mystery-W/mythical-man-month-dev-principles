# 决策工作表与案例

只使用当前阶段需要的部分。下面的字段用于帮助思考，不要求每次对话或每个函数都填写，也不要求自动生成新文档。已有材料能回答时直接复用。

## 启动或架构级调整：一页开发约定

| 要回答的问题 | 应留下的最小有用结论 |
| --- | --- |
| 为谁解决什么问题 | 目标用户、真实任务、成功结果 |
| 本次交付到哪里 | 原型、内部工具、试用增量或发布；明确不做什么 |
| 哪些概念必须统一 | 对象身份、状态、单位、保存及错误规则 |
| 用户在哪里使用 | 平台、硬件、依赖、模型、安装升级与数据位置 |
| 最大未知是什么 | 能推翻当前方案的假设、最小检验与停止条件 |
| 什么限制会影响方案 | 时间、内存、响应、可维护性；待测值不假装已确定 |
| 怎样增长 | 第一个可检查闭环、下一个增量、反馈来自谁 |
| 怎样保护已有成果 | 当前可信版本、数据副本、兼容与迁移策略 |
| 怎样验收 | 可观察事件、代表性条件、证据与未覆盖范围 |

启动讨论优先解释会改变方向的事项。对次要细节采用合理假设并记录；不要拿一张大清单让初次开发者逐项回答陌生术语。

## 开始一批改动前：检查是否值得做、是否可控制

- **动机：** 用户问题还是实现者偏好？当前证据是什么？不做的后果是什么？
- **边界：** 哪些概念、接口、持久化数据或用户操作会变？哪些地方存在真实依赖？
- **替代：** 是否有更小的改动、成熟组件或先验证再扩展的路径？比较总成本，不只比较代码量。
- **恢复：** 当前状态是否可找回？快照覆盖什么？迁移是否可逆？分支是否误被当成了备份？
- **完成：** 本批次有哪些可观察的通过条件？什么新证据会使我们调整或停止方案？

小修复可能只需两句话回答动机与完成；跨版本数据迁移则应真正检查恢复路径。

## 一个增量完成时：验收与版本提醒

用事实填写，不用“应该没问题”。按变更风险选取项目：

| 维度 | 记录内容 |
| --- | --- |
| 本次实现 | 当前确实可用的用户行为，关联版本或差异 |
| 验证范围 | 哪类检查、什么环境、什么数据、什么结果 |
| 重要边界 | 未覆盖、已失败及其对用户的影响 |
| 使用与恢复 | 启动、主要流程、保存重开、异常或恢复中与本次相关的检查 |
| 说明 | 相关操作说明、接口语义和重要理由是否已同步 |
| 版本状态 | 工作区是否混杂其他改动，是否已有可恢复检查点 |
| 下一步 | 本批次可以交付，还是仍缺关键条件；不要把必要修复静默推成未来优化 |

不要把功能验收、跨电脑验收、研究准确性验证写成同一件事。样例可运行不能证明所有输入正确，模拟数据通过不能证明真实场景精度。

需要提醒存档时，说明：当前证据、建议的检查点、提交如何拆分、是否需要分支或发布标签，以及尚未执行的动作。遵守当前授权，不默认推送。

## 延期、连续失败或大改冲动：复盘卡

1. 当前可确认的事实是什么？哪些只是感觉？
2. 原计划哪项假设失效：需求、依赖、性能、可分工性、环境还是估算口径？
3. 目前真正的瓶颈在哪？更多编码能解决它吗？
4. 哪个已完成成果值得保留？怎样恢复可信基线或降低持续影响？
5. 可选动作有哪些：缩范围、补验证、调整接口、延后日期、复用组件、增加独立产能？
6. 推荐动作的收益、代价与停止条件是什么？
7. 改进后观察什么结果，避免下次凭同一感觉再作判断？

不要把复盘写成自责。“我太粗心”不能指导行动；“迁移前没有读取旧版本样本，且没有可恢复副本”才指向具体改进。

## 四个应用示例

### 已有项目有很多未提交修改，准备继续重构

先查看实际差异及当前验证状态，识别独立修改与混杂工作。提醒建立可恢复检查点，说明分支不保存未提交内容；按用户授权采取提交或非破坏性快照等方案。已有改动不能为了整洁而丢弃。未达到发布标准不妨碍诚实标记的工作检查点，也不应被贴成正式发布。

避免的另一极端：因为工作区不干净而拒绝所有诊断，或每完成一轮编辑就要求发版、推送和打标签。

### “这次必须做到最好，把UI全部定稿再写代码”

先问或从现有材料确定用户任务与主要未知。如果大文件处理能否成立会决定界面，就先做小范围性能与流程实验，配合交互草图；把结果带回设计。若只是已有流程的视觉完善，则可以先完成相应界面设计。保持本次质量要求，允许设计根据证据改变。

避免的另一极端：用增量开发为借口不考虑用户流程，先堆功能再说。

### “只修这个中文路径下无法保存的错误”

定位相关路径处理和失败边界，做针对性修复，用中文与空格路径、必要的原有路径场景检查保存结果。若涉及持久化，再确认文件可重开。更新相关说明即可；没有证据表明需要重构全应用时，不启动架构审计或强制填写项目启动表。

避免的另一极端：为了最小改动而只屏蔽异常，留下未保存却显示成功的行为。

### “开发机跑通了，马上发布给别人”

核对发布目标、依赖与已验证范围，检查首次使用的关键路径。若还没在代表性目标环境验证，明确缺少的证据和可做的检查。用户若选择受限试用，可给出与证据相符的试用说明；不能称为已通过全面兼容验收。权限允许的准备工作继续完成，外部发布按用户授权执行。

避免的另一极端：要求验证世界上所有电脑，否则永远不能发布。
